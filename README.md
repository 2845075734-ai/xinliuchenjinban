✨ 功能特性

- 🧠 多维度评分判断 — 基于相关性、意愿度、社交性、时效性、连续性五个维度综合评估
- 🌊 沉浸模式 — Bot 决定回复后自动进入沉浸模式，持续参与对话
- 🤖 小模型决策 — 使用轻量级模型判断是否回复，降低开销
- 🎯 Bot发言感知 — 小模型重点追踪 Bot 自己的发言，精准判断对话连贯性
- ⏳ 消息防抖 — 判定回复后延迟触发，期间有新消息自动重置计时，防止插嘴
- 🛡️ 防零分机制 — 评分范围1-10分，避免模型返回0分影响判断
- ⏸️ 智能暂停 — Bot 回复前自动暂停判断，防止小模型连续判定需要回复，导致反映慢的大模型按顺序一个个回复，别人都聊完了还在回复
- 📊 消息缓冲 — 智能消息记录与去重，保证上下文连贯
- ✏️ 自定义提示词 — 支持自定义评判提示词，灵活控制判断逻辑
- 🎚️ 动态阈值 — 根据群聊活跃度自动调整回复阈值，活跃时少说话，冷淡时多说话
- 🆕 🔊 详细日志开关 — 平时只输出关键日志，调试时一键开启完整判断日志

⚙️ 配置说明

基础配置

    enable_heartflow (bool, 默认 false) — 是否启用心流插件
    judge_provider_name (string, 默认 "") — 小模型提供商名称
    reply_threshold (float, 默认 0.6) — 回复触发阈值，范围 0.0~1.0

评分权重配置

每个维度分数范围 1-10分（避免0分），最终加权计算综合得分：

    judge_relevance (默认 0.25) — 相关性：消息与 Bot 角色的关联程度
    judge_willingness (默认 0.20) — 意愿度：Bot 参与对话的意愿
    judge_social (默认 0.20) — 社交性：回复是否符合社交礼仪
    judge_timing (默认 0.15) — 时效性：当前时机是否适合插入
    judge_continuity (默认 0.20) — 连续性：是否回应了 Bot 的发言或延续对话

注意：权重之和应为 1.0，不为 1.0 时插件会自动归一化。

高级配置

    context_messages_count (int, 默认 5, 范围 1-30) — 上下文消息数量
    judge_context_count (int, 默认 10, 范围 1-50) — 判断参考消息数量，建议比上下文消息数更大以提升判断质量
    judge_max_retries (int, 默认 3, 范围 0-10) — 小模型调用重试次数
    immersive_mode_duration (int, 默认 30, 范围 0-300) — 沉浸模式持续时间(秒)
    judgment_paused_timeout (int, 默认 60, 范围 5-300) — 判断暂停超时保护(秒)
    judge_include_reasoning (bool, 默认 true) — 是否输出推理过程
    whitelist_enabled (bool, 默认 false) — 是否启用白名单
    chat_whitelist (list, 默认 []) — 白名单群聊 ID 列表

🆕 日志配置

    enable_detailed_log (bool, 默认 false) — 详细日志开关

    关闭时（默认）：
      仅在【触发回复】【警告】【错误】时输出日志，控制台保持清爽

    开启时：
      输出每次判断的完整日志，包括五维评分详情、跳过原因、
      判断理由、暂停/恢复状态变化、防抖过程等

    也可以随时使用 /heartflow_log 指令在运行时切换，
    无需重启（重启后恢复此配置值）。

⏳ 防抖配置

    enable_debounce (bool, 默认 true) — 是否启用回复防抖
    debounce_delay (float, 默认 2.0, 范围 0.5-10.0) — 基础防抖延迟（秒）
    max_debounce_wait (float, 默认 5.0, 范围 1.0-15.0) — 最大防抖等待（秒）

    工作流程：
      判定需要回复 → 等待 debounce_delay 秒
        ├─ 期间无新消息 → 触发回复
        ├─ 期间有新消息 → 重置计时，以最新消息为准重新等待
        └─ 等待超过 max_debounce_wait → 强制触发，防止无限等待

    特殊规则：防抖期间若有用户明确 @Bot，防抖任务自动取消，
    交由正常唤醒流程处理，避免重复回复。

🎚️ 动态阈值配置

    enable_dynamic_threshold (bool, 默认 false) — 是否启用动态阈值
    dynamic_threshold_max (float, 默认 0.85) — 活跃度最高时的阈值上限（火热时更克制）
    dynamic_threshold_min (float, 默认 0.35) — 活跃度最低时的阈值下限（冷清时更主动）
    dynamic_activity_window (int, 默认 300) — 计算活跃度的时间窗口（秒）
    dynamic_activity_weights (str, 默认 "0.4,0.3,0.3") — 活跃度权重，依次为：消息频率、消息间隔、参与人数。用逗号分隔，三个权重会被自动归一化。

动态阈值会根据群聊实时活跃度，在 [dynamic_threshold_min, dynamic_threshold_max] 区间内平滑调整触发阈值。活跃度越高，阈值越接近上限（Bot 更少打扰）；活跃度越低，阈值越接近下限（Bot 更主动暖场）。

✏️ 自定义评判提示词

你可以在配置中设置 judge_prompt 来完全自定义评判逻辑。留空则使用内置默认提示词。

V1.4.0 内置提示词的重要变化：
内置模板现在会明确要求小模型【优先关注 Bot 自己的发言】——
对话历史中 role 为 assistant 的消息是 Bot 说的话，role 为 user 的消息
是群友说的话（带 [昵称] 前缀）。小模型会先回顾 Bot 最近说了什么，
再判断当前消息是否是对 Bot 发言的回应、追问或话题延续。
如果你自定义提示词，建议保留这一引导思路。

必须包含的占位符

在自定义提示词中，你需要使用以下占位符（用 {} 包裹）：

    {score_min} — 最低分数 (示例: 1)
    {score_max} — 最高分数 (示例: 10)
    {mid} — 中间分数 (示例: 5)
    {message} — 当前待判断的消息内容 (示例: "今天天气真好")
    {sender_name} — 消息发送者的名称 (示例: "用户A")
    {chat_id} — 群聊标识符 (示例: "group_12345")
    {minutes_since_reply} — 距离上次回复的分钟数 (示例: 5)
    {threshold} — 回复触发阈值 (示例: 0.6)
    {chat_context} — 当前群聊上下文信息 (示例: "活跃度:高 | 回复率:5.2%")
    {chat_flow} — 对话流向分析 (示例: "闲聊")
    {last_bot_reply} — Bot上一次的回复内容 (示例: "你好！")
    {reasoning_part} — 推理输出部分（内部使用）
    {activity_level} — 当前活跃度数值 (示例: 0.65)
    {activity_desc} — 当前活跃度描述 (示例: "💬一般活跃")

返回格式要求

你的提示词必须要求模型返回 JSON 格式，且包含以下字段：

    {
      "relevance": 7,
      "willingness": 6,
      "social": 8,
      "timing": 5,
      "continuity": 7,
      "reasoning": "消息是关于编程的提问，Bot可以回答"
    }

字段说明：

- relevance ~ continuity：五个评分维度，值为 {score_min} 到 {score_max} 之间的数字
- reasoning：简短的原因说明（可选，由 judge_include_reasoning 配置控制）

完整示例：简化版提示词

    你是消息判断助手。

    ## 待判断消息
    [{sender_name}] {message}

    ## 判断规则
    - 如果消息是提问（包含?或吗等），各维度给高分（{mid}-{score_max}）
    - 如果消息是陈述句，各维度给低分（{score_min}-{mid}）
    - 所有分数必须在 {score_min} 到 {score_max} 之间，不能为0

    ## 返回格式
    严格返回JSON：
    {{"relevance": 分数, "willingness": 分数, "social": 分数, "timing": 分数, "continuity": 分数, "reasoning": "原因"}}

完整示例：角色扮演场景（傲娇角色）

    你是傲娇机器人的决策系统，判断是否应该回复。

    ## 性格特点
    - 表面上不想理人，实际上很热心
    - 喜欢被需要的感觉
    - 对技术问题特别感兴趣

    ## 重要提醒
    - 对话历史中 assistant 消息是你（机器人）之前说的话
    - 如果当前消息是在回应你之前的发言，continuity 给高分

    ## 评分标准 ({score_min}-{score_max}分)

    ### 高分情况 ({mid}-{score_max})
    - 有人问技术问题 → relevance: 9
    - 有人求助 → willingness: 8
    - 群里在聊技术话题 → social: 8

    ### 低分情况 ({score_min}-{mid})
    - 纯闲聊 → relevance: 3
    - 有人在秀恩爱 → social: 2
    - 刚回复过 → timing: 2

    ## 当前状态
    - 上次回复: {minutes_since_reply}分钟前
    - 上次Bot回复: {last_bot_reply}

    ## 待判断消息
    [{sender_name}] {message}

    ## 返回格式
    分数范围 {score_min}-{score_max}，不能为0。
    {{"relevance": 分, "willingness": 分, "social": 分, "timing": 分, "continuity": 分, "reasoning": "傲娇分析"}}

提示词编写技巧

1. 明确分数范围：在提示词中多次强调"所有分数必须在 X 到 Y 之间，不能为0"
2. 给出具体示例：告诉模型什么情况给高分，什么情况给低分
3. 强调 Bot 发言：提醒模型对话历史中的 assistant 消息是 Bot 自己说的话，回应 Bot 的消息应给高连贯性分数
4. 利用上下文：使用 {chat_context} 和 {chat_flow} 让模型了解群聊氛围
5. 保持简洁：提示词过长会增加小模型的处理负担
6. 测试调试：开启详细日志（/heartflow_log）查看每次判断的评分和理由

📊 评分系统详解

评分范围

- 分数范围：1-10分（最低1分，避免0分）
- 默认分数：5分（解析失败或异常时使用）
- 中间值：5.5分

五个评分维度

    relevance     相关性    消息与Bot的关联程度
    willingness   意愿度    Bot参与对话的意愿
    social        社交性    回复是否符合社交礼仪
    timing        时效性    当前时机是否适合插入
    continuity    连续性    是否回应了Bot的发言或延续对话

阈值计算

    配置阈值: 0.6 (0-1范围)
    绝对阈值: 1 + (10-1) × 0.6 = 6.4分

    即: 5个维度加权平均分需达到 6.4分 才触发回复

🎚️ 动态阈值（可选）

启用动态阈值后，触发阈值不再固定，而是根据群聊活跃度自动浮动：

1. 活跃度计算
   基于 dynamic_activity_window 内的用户消息，综合三个维度：
   - 消息频率（条/分钟）
   - 平均消息间隔（秒）
   - 参与人数
   最终输出 0.0 ~ 1.0 的活跃度指标，其中 1.0 表示非常火热，0.0 表示几乎无人说话。

2. 阈值映射
   活跃度越高（群聊火热），阈值越接近 dynamic_threshold_max，Bot 更克制；
   活跃度越低（群聊冷清），阈值越接近 dynamic_threshold_min，Bot 更主动。
   中间区域采用平滑曲线，避免阈值频繁跳变。

3. 效果对比
   - 若无动态阈值：阈值始终为 reply_threshold（例如 0.6）
   - 启用动态阈值：
     - 火热时阈值可能升至 0.85 → 需要更高评分才回复，减少插嘴
     - 冷清时阈值可能降至 0.35 → 更容易触发回复，主动暖场

使用 /heartflow 命令可实时查看当前活跃度、动态阈值及绝对触发分数。

防零分机制

    第1层 | 提示词引导 | 明确告知模型"最低1分，不能为0"
    第2层 | 安全提取 | safe_extract_score() 捕获并修正0分
    第3层 | 范围限制 | clamp_score() 最终兜底

🌊 沉浸模式详解

触发与退出

    触发条件: Bot判断应该回复时，自动激活
    持续时间: 配置的 immersive_mode_duration (默认30秒)
    倒计时刷新: Bot每次回复后，倒计时自动刷新
    退出机制: 倒计时结束后自动退出

沉浸模式下的判断逻辑

沉浸模式的聊天记录中，🤖 Bot 开头的消息是机器人自己说的话，
👤 开头的是群友说的话。小模型会先追踪 Bot 的发言链路再判断。

会回复的情况：

1. 消息直接 @ 了机器人
2. 消息明确向机器人提问
3. 机器人发起的对话的延续（回应了 🤖 Bot 的发言）
4. 消息内容与机器人刚刚的话题直接相关
5. 群聊中出现了冷场，机器人的回复能自然活跃气氛

不会回复的情况：

- 两个用户之间的正常闲聊
- 用户之间的问答互动
- 简单的表情包、语气词
- 与机器人之前发言毫无关联的新话题

- 📊 每次评分判断的完整五维得分与跳过原因

- 消息过滤原因（@他人、指令、唤醒等）

💡 使用建议

    场景              建议
    阈值调节          默认 0.6 适合大多数场景。回复太频繁就调高，回复太少就调低
    沉浸时长          建议 30-60 秒。太短会频繁进出，太长可能过度活跃
    小模型选择        判断逻辑不需要太强的模型，轻量级即可
    白名单            建议仅在需要 Bot 主动参与的群聊中启用
    自定义提示词      简洁优先，明确分数范围，给出高分/低分示例，强调关注 Bot 发言
    动态阈值调整      一般保持默认范围即可。若希望 Bot 在冷清时极其主动，可调低 dynamic_threshold_min；若希望火热时几乎不插话，可调高 dynamic_threshold_max
    防抖调节          默认 2秒/最大5秒 适合多数场景。群友打字慢或喜欢分段发消息，可调高 debounce_delay 至 3-4 秒
    日志使用          平时保持关闭；Bot 行为异常时用 /heartflow_log 临时开启，观察判断过程，调完再关闭

❓ 常见问题

Q: Bot 完全不主动回复怎么办？

1. 确认 enable_heartflow 为 true
2. 检查 judge_provider_name 是否正确配置
3. 尝试调低 reply_threshold 至 0.4
4. 使用 /heartflow_log 开启详细日志，观察每次判断的评分
5. 使用 /heartflow_debug 查看消息是否被正常记录

Q: Bot 回复太频繁怎么办？

1. 调高 reply_threshold 至 0.75-0.85
2. 增大 immersive_mode_duration 至 60-120秒
3. 降低评分权重中的 willingness 值

Q: 沉浸模式一直不触发？

1. 确保 Bot 有正常响应能力
2. 检查白名单设置（如启用了白名单）
3. 开启详细日志查看判断过程

Q: 评分出现0分怎么办？

本版本已内置防零分机制：

- 评分范围为1-10分
- 即使模型返回0分，也会自动修正为1分
- 异常情况下使用5分作为默认值

Q: 如何查看心流判断的详细日志？

1. 使用 /heartflow_log 指令即时开启详细日志（管理员，推荐）
2. 或在插件配置中开启 enable_detailed_log（持久生效）
3. 使用 /heartflow_debug 查看消息记录
4. 在 AstrBot 日志中搜索 [心流] 关键字

Q: 控制台日志太多刷屏怎么办？

确认 enable_detailed_log 为 false（默认即关闭）。
关闭后只有触发回复、警告、错误才会输出日志。

Q: 自定义提示词不生效？

1. 确保提示词中包含所有必要的占位符（见上方占位符列表）
2. 检查提示词格式是否正确（JSON中的花括号需要双写 {{}} ）
3. 查看日志是否有"提示词模板格式化失败"的错误

Q: 动态阈值好像没效果？

1. 确认 enable_dynamic_threshold 已设为 true
2. 检查 dynamic_activity_window 是否过大导致活跃度变化缓慢（可适当调小，如 120 秒）
3. 使用 /heartflow 命令查看当前活跃度和动态阈值是否变化
4. 确保 dynamic_threshold_min 和 dynamic_threshold_max 差值足够明显（建议差值 ≥ 0.2）

Q: Bot 总是打断别人说话？

1. 确认 enable_debounce 已开启（默认开启）
2. 调大 debounce_delay（如 3-4 秒），给群友更多把话说完的时间
3. 调大 max_debounce_wait（如 8-10 秒），容忍更长的连续发言

Q: 小模型好像不理解对话上下文，Bot 说过的话被无视？

V1.4.0 已针对此问题全面优化：
1. 内置提示词已明确要求小模型优先关注 assistant（Bot）的发言
2. 群友消息已添加 [昵称] 前缀，便于区分发言者
3. 已修复对话历史顺序问题
4. 如使用自定义提示词，请参照"提示词编写技巧"第3条补充相关引导
5. 可适当调大 judge_context_count（如 15-20），让小模型看到更长的对话链路
