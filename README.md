# 心流沉浸版 (Heartflow Plugin)

> 修改自心流插件，通过小模型多维度评分，实现智能群聊主动回复系统。

---

## 简介

本插件是 AstrBot 的群聊主动回复增强工具，通过轻量级小模型对群消息进行多维度评分，智能判断是否介入对话，兼顾回复质量与群聊体验。支持动态阈值、沉浸模式、消息防抖、群聊独立配置等功能，完全依赖 AstrBot 原生对话流管理上下文，无额外 token 浪费。

## ✨ 功能特性

- 🧠 **多维度评分判断** — 基于相关性、意愿度、社交性、时效性、连续性五个维度综合评估
- 🌊 **沉浸模式** — Bot 决定回复后自动进入沉浸模式，持续参与对话
- 🤖 **小模型决策** — 使用轻量级模型判断是否回复，降低开销
- 🎯 **Bot 发言感知** — 小模型重点追踪 Bot 自己的发言，精准判断对话连贯性
- ⏳ **消息防抖** — 判定回复后延迟触发，期间仅合并触发者的文本消息，不重置计时，到点立即触发，防止插嘴
- 🛡️ **防零分机制** — 评分范围 1-10 分，避免模型返回 0 分影响判断
- ⏸️ **智能暂停** — Bot 回复前自动暂停判断，防止小模型连续判定需要回复，导致响应慢的大模型按顺序逐个回复
- 📊 **消息缓冲** — 智能消息记录与去重，保证上下文连贯
- ✏️ **自定义评分规则** — 支持通过 WebUI 可视化编辑五个维度的低分/高分描述和权重，灵活控制判断逻辑
- 🎚️ **动态阈值** — 根据群聊活跃度自动调整回复阈值，活跃时少说话，冷淡时多说话
- 🆕 **详细日志开关** — 平时只输出关键日志，调试时一键开启完整判断日志

> **注意**：本插件**不注入自定义上下文**到大模型，完全依赖 AstrBot 原生的 ConversationManager 管理对话历史，避免上下文重复和 token 浪费。

## ⚙️ 配置说明

### 基础配置

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| enable_heartflow | bool | false | 是否启用心流插件 |
| judge_provider_name | string | "" | 小模型提供商名称（建议使用快速小模型） |
| reply_threshold | float | 0.6 | 回复触发阈值，范围 0.0~1.0 |

### 评分规则配置

每个维度分数范围 **1-10 分**（避免 0 分），最终加权计算综合得分：

| 维度 | 默认权重 | 说明 |
|------|----------|------|
| relevance（相关性） | 0.25 | 消息与 Bot 角色的关联程度 |
| willingness（意愿度） | 0.20 | Bot 参与对话的意愿 |
| social（社交性） | 0.20 | 回复是否符合社交礼仪 |
| timing（时效性） | 0.15 | 当前时机是否适合插入 |
| continuity（连续性） | 0.20 | 是否回应了 Bot 的发言或延续对话 |

**注意**：权重之和应为 1.0，不为 1.0 时插件会自动归一化。

你可以在 WebUI 的 judge_rules 配置中，为每个维度自定义：

- **dimension_display**：维度中文名（显示用）
- **weight**：权重（0.0-1.0）
- **low_desc**：低分情况描述（什么情况给低分）
- **high_desc**：高分情况描述（什么情况给高分）

### 高级配置

| 配置项 | 类型 | 默认值 | 范围 | 说明 |
|--------|------|--------|------|------|
| context_messages_count | int | 5 | 1-50 | 对话流分析消息数：小模型分析对话流时读取的最近消息条数 |
| judge_context_count | int | 10 | 1-50 | 判断模型上下文条数：传给小模型评分的历史对话条数 |
| judge_max_retries | int | 3 | 0-5 | 小模型调用重试次数（建议不超过 5 次） |
| immersive_mode_duration | int | 30 | 0-300 | 沉浸模式持续时间（秒）。设为 0 禁用 |
| judgment_paused_timeout | int | 60 | 15-300 | 判断暂停超时保护（秒），防止永久暂停 |
| judge_include_reasoning | bool | true | - | 是否输出推理过程 |
| whitelist_enabled | bool | false | - | 是否启用白名单 |
| chat_whitelist | list | [] | - | 白名单群聊 ID 列表 |

### 日志配置

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| enable_detailed_log | bool | false | 详细日志开关 |

关闭时（默认）：仅在触发回复、警告、错误时输出日志，控制台保持清爽。

开启时：输出每次判断的完整日志，包括五维评分详情、跳过原因、判断理由、暂停/恢复状态变化、防抖过程等。

也可以随时使用 /heartflow_log 指令在运行时切换，无需重启（重启后恢复此配置值）。

### 防抖配置

| 配置项 | 类型 | 默认值 | 范围 | 说明 |
|--------|------|--------|------|------|
| enable_debounce | bool | true | - | 是否启用回复防抖 |
| debounce_delay | float | 2.0 | 0.5-10.0 | 基础防抖延迟（秒）：判定需要回复后，等待多少秒再实际触发 |
| max_debounce_wait | float | 5.0 | 1.0-15.0 | 最大防抖等待（秒）：最多等待多少秒后也必须触发回复 |

工作流程：

1. 判定需要回复 → 启动防抖（固定等待 debounce_delay 秒）
2. 防抖期间：触发者本人发消息 → 文本追加到待合并列表，**不重置计时器**；其他群成员发消息 → 完全忽略
3. 达到 debounce_delay → **立即触发**回复（合并触发者的所有文本）
4. 达到 max_debounce_wait → **强制触发**，防止无限等待

特殊规则：防抖期间若有用户明确 @Bot 或发送指令，防抖任务自动取消，交由正常唤醒流程处理。

### 动态阈值配置

| 配置项 | 类型 | 默认值 | 范围 | 说明 |
|--------|------|--------|------|------|
| enable_dynamic_threshold | bool | false | - | 是否启用动态阈值 |
| dynamic_threshold_max | float | 0.85 | 0.5-1.0 | 活跃度最高时的阈值上限（火热时更克制） |
| dynamic_threshold_min | float | 0.35 | 0.0-0.5 | 活跃度最低时的阈值下限（冷清时更主动） |
| dynamic_activity_window | int | 300 | 60-600 | 计算活跃度的时间窗口（秒） |
| dynamic_activity_weights | string | "0.4,0.3,0.3" | - | 活跃度权重，依次为：消息频率、消息间隔、参与人数 |

动态阈值原理：启用后，触发阈值不再固定，而是根据群聊实时活跃度，在 [dynamic_threshold_min, dynamic_threshold_max] 区间内平滑调整。活跃度越高阈值越接近上限（Bot 更克制），活跃度越低阈值越接近下限（Bot 更主动）。

使用 /heartflow 命令可实时查看当前活跃度、动态阈值及绝对触发分数。

## 📊 评分系统详解

### 评分范围

- 分数范围：**1-10 分**（最低 1 分，避免 0 分）
- 默认分数：5 分（解析失败或异常时使用）
- 中间值：5.5 分

### 阈值计算

配置阈值: 0.6 (0-1 范围)

绝对阈值: 1 + (10-1) x 0.6 = 6.4 分

即：5 个维度加权平均分需达到 **6.4 分** 才触发回复。

### 防零分机制

| 层级 | 机制 | 说明 |
|------|------|------|
| 第 1 层 | 提示词引导 | 明确告知模型"最低 1 分，不能为 0" |
| 第 2 层 | 安全提取 | safe_extract_score() 捕获并修正 0 分 |
| 第 3 层 | 范围限制 | clamp_score() 最终兜底 |

## 🌊 沉浸模式详解

### 触发与退出

- **触发条件**：Bot 判断应该回复时，自动激活
- **持续时间**：配置的 immersive_mode_duration（默认 30 秒）
- **倒计时刷新**：Bot 每次回复后，倒计时自动刷新
- **退出机制**：倒计时结束后自动退出

### 沉浸模式下的判断逻辑

沉浸模式下，小模型的默认倾向是 **不回复**，只有在以下情况之一时才回复：

1. 消息直接 @ 了机器人或提到机器人名字
2. 消息明确向机器人提问
3. 消息是机器人发起的对话的延续（回应了 Bot 的发言）
4. 消息内容与机器人刚聊的话题直接相关
5. 群聊中出现冷场，机器人的回复能自然活跃气氛

不会回复的情况：

- 两个用户之间的正常闲聊
- 用户之间的问答互动
- 简单的表情包、语气词
- 与机器人之前发言毫无关联的新话题

## ⏸️ 智能暂停机制

为防止 Bot 连续发送多条回复：

Bot 判定回复 → 暂停判断 → Bot 发送消息 → 恢复判断

超时保护(默认 60 秒) → 自动恢复

## 💡 使用建议

| 场景 | 建议 |
|------|------|
| **阈值调节** | 默认 0.6 适合大多数场景。回复太频繁就调高，回复太少就调低 |
| **沉浸时长** | 建议 30-60 秒。太短会频繁进出，太长可能过度活跃 |
| **小模型选择** | 判断逻辑不需要太强的模型，轻量级即可 |
| **白名单** | 建议仅在需要 Bot 主动参与的群聊中启用 |
| **动态阈值** | 一般保持默认范围即可。若希望 Bot 在冷清时极其主动，可调低 dynamic_threshold_min |
| **防抖调节** | 默认 2 秒/最大 5 秒适合多数场景。群友打字慢可调高 debounce_delay 至 3-4 秒 |
| **日志使用** | 平时保持关闭；Bot 行为异常时用 /heartflow_log 临时开启 |

## ❓ 常见问题

### Q: Bot 完全不主动回复怎么办？

1. 确认 enable_heartflow 为 true
2. 检查 judge_provider_name 是否正确配置
3. 尝试调低 reply_threshold 至 0.4
4. 使用 /heartflow_log 开启详细日志，观察每次判断的评分
5. 使用 /heartflow_debug 查看消息是否被正常记录

### Q: Bot 回复太频繁怎么办？

1. 调高 reply_threshold 至 0.75-0.85
2. 增大 immersive_mode_duration 至 60-120 秒
3. 在 judge_rules 中降低 willingness（意愿度）的权重

### Q: 沉浸模式一直不触发？

1. 确保 Bot 有正常响应能力
2. 检查白名单设置（如启用了白名单）
3. 开启详细日志查看判断过程

### Q: 评分出现 0 分怎么办？

本版本已内置防零分机制：

- 评分范围为 1-10 分
- 即使模型返回 0 分，也会自动修正为 1 分
- 异常情况下使用 5 分作为默认值

### Q: 如何查看心流判断的详细日志？

1. 使用 /heartflow_log 指令即时开启详细日志（管理员，推荐）
2. 或在插件配置中开启 enable_detailed_log（持久生效）
3. 使用 /heartflow_debug 查看消息记录
4. 在 AstrBot 日志中搜索 [心流] 关键字

### Q: 控制台日志太多刷屏怎么办？

确认 enable_detailed_log 为 false（默认即关闭）。关闭后只有触发回复、警告、错误才会输出日志。

### Q: 自定义评分规则不生效？

1. 确保在 WebUI 的 judge_rules 中正确填写了五个维度的配置
2. 检查权重是否为正数（会自动归一化）
3. 查看日志是否有配置解析错误

### Q: 动态阈值好像没效果？

1. 确认 enable_dynamic_threshold 已设为 true
2. 检查 dynamic_activity_window 是否过大导致活跃度变化缓慢
3. 使用 /heartflow 命令查看当前活跃度和动态阈值是否变化
4. 确保 dynamic_threshold_min 和 dynamic_threshold_max 差值足够明显（建议差值大于等于 0.2）

### Q: Bot 总是打断别人说话？

1. 确认 enable_debounce 已开启（默认开启）
2. 调大 debounce_delay（如 3-4 秒），给群友更多把话说完的时间
3. 调大 max_debounce_wait（如 8-10 秒），容忍更长的连续发言

### Q: 小模型好像不理解对话上下文，Bot 说过的话被无视？

V1.4.0 已针对此问题全面优化：

1. 内置提示词已明确要求小模型优先关注 assistant（Bot）的发言
2. 群友消息已添加 [昵称] 前缀，便于区分发言者
3. 已修复对话历史顺序问题
4. 可适当调大 judge_context_count（如 15-20），让小模型看到更长的对话链路

## 🔧 技术细节

### 上下文说明

本插件**不注入自定义上下文**到大模型，完全依赖 AstrBot 原生的 ConversationManager 管理对话历史。插件仅维护一份本地消息缓冲区（_raw_msg_buffer），用于：

1. 小模型评分时读取历史消息（滑动窗口，自动淘汰旧消息）
2. 分析对话流（话题提取、连续性判断）
3. 记录 Bot 自身的回复，用于连续性评分

缓冲区大小自动管理，无需担心内存泄漏。
